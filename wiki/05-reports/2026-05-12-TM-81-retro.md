# TM-81 retro — `src/lib/usage.ts` prisma → client bundle guard

## Summary

Discovered by TM-78 r2 QA iteration 2: turbopack errored with
`the chunking context (unknown) does not support external modules
(request: node:fs)` because `src/lib/usage.ts` top-level imports
`@/lib/db/prisma` (which transitively pulls `node:fs` via @prisma/client),
and `PromptPanel.tsx` (a `'use client'` component) was importing
`TIER_LIMITS` from `@/lib/usage`. That dragged prisma + `node:fs` into the
browser bundle, breaking the dev overlay and making `/studio` unreachable.

## Root cause (re-confirmed at TM-81)

Two-layer issue:

1. `usage.ts` has a legitimate top-level `import { prisma } from
   '@/lib/db/prisma'` — it owns the atomic `reserveEditSlot` /
   `refundEditSlot` raw-SQL helpers (TM-93). That import is fine *if* only
   server modules reach `usage.ts`.
2. `usage.ts` re-exported `TIER_LIMITS`, and at TM-78 r2 the client-side
   `PromptPanel` was still pulling `TIER_LIMITS` from `@/lib/usage`. The
   import graph collapsed prisma into the client chunk.

TM-98 already extracted `TIER_LIMITS` into a leaf `src/lib/tier-limits.ts`
(no prisma, no fs) and switched `PromptPanel` over. So by the time TM-81
landed, the active import graph from client → prisma was already broken.
However nothing prevented a future regression — any client component that
re-added `import { TIER_LIMITS } from '@/lib/usage'` would silently reopen
the bundle leak.

## Fix

Add `import 'server-only'` to the top of `src/lib/usage.ts`. The sentinel
(provided by `next` itself, version 16.2.4 ships `server-only@0.0.1`) makes
any client-side import of this module fail at build time with a clear
error, converting a silent bundle pull of prisma + `node:fs` into a
loud, fixable build failure.

Minimal diff (single file): a 10-line comment block + `import 'server-only'`
at the top of `src/lib/usage.ts`. No behavior change for the 5 server
importers (`/api/{edit,generate,upload,usage}` routes, `/dashboard`
server component). `TIER_LIMITS` re-export from usage.ts is preserved for
backwards compatibility — only its client-side use would now fail.

## Verification (live, this branch)

- **Repro before fix**: `/studio` (after TM-98) already loads HTTP 200 with
  no Build Error overlay — the active bug is no longer triggered because
  PromptPanel correctly imports from `@/lib/tier-limits`. The risk is
  *future regression*; the server-only sentinel makes that regression
  fail loudly at build time. Verified by running
  `PORT=3081 HOSTNAME=127.0.0.1 npm run dev` on `5a8efb3` (pre-fix HEAD)
  and curling `/studio` (after dev auto-login) — HTML response is the full
  app shell, no error markers (`Build Error`, `node:fs`, `chunking`,
  `nextjs-portal`).
- **After fix**: same dev session, `/studio` → HTTP 200, `/dashboard` →
  HTTP 200 (server component still imports `TIER_LIMITS` from
  `@/lib/usage` and gets it cleanly because it runs on the server).
- **`npm run build`**: passes (7.3s compile, all 21 pages emitted, no
  prisma-in-client error).
- **`npx tsc --noEmit`**: same 3 pre-existing errors as `git stash`
  baseline (benchmarks/tm-71-validate.ts, evaluator-fuzz.test.ts —
  unrelated). Zero new TypeScript errors.
- **`npm run lint`**: same 74 pre-existing errors as baseline (all in
  unrelated bundled artifact files >10000 lines). Zero new lint errors.
- **`jest __tests__/lib/usage*.test.ts`**: 13/13 pass.

## What unblocked

- TM-78 r2 had flagged this as `blocks_live_qa=true` and
  `triggers_requalify=[TM-78]`. With server-only guard in place, future
  client-side regression of `usage.ts` import is caught at build, so the
  live-qa block is permanently mitigated rather than relying on convention.
- TM-79 (player controls QA) — task spec listed it as downstream; current
  HEAD already loads `/studio` cleanly, so this fix doesn't unblock new
  ground but does pin the invariant.

## Why not something bigger

The task description suggested two fix ideas: (a) split `TIER_LIMITS` into
a client-safe file, or (b) mark `usage.ts` as `'server-only'`. Option (a)
was already done in TM-98. Option (b) is exactly this PR — and it's the
remaining defense-in-depth piece. No ADR is required: it's a small import
sentinel, not an architectural shift. Existing ADR-0001 (Edit ≠ Render) is
unaffected.
