# TM-160 retro — SSE real progress bar from stage marks

## Goal

Replace the TM-91 client-side timer-driven progress bar with **real
server-side stage progress** delivered via SSE. TM-156 already
instruments every phase boundary in the generate stack via
`recordMark()`; this task plumbs those marks to a browser EventSource
so the user sees `구성을 짜는 중 → 캐릭터 일러스트 생성 중 → 코드
합치는 중 → 마무리 중` instead of a logistic guess.

Depends on TM-156 (latency-profile.ts) and TM-91 (timer fallback retained).

## What landed

### Server

- **`src/lib/ai/progress-bus.ts`** — new in-memory pub/sub keyed by a
  client-generated `progressId`. Buffered (64 events), TTL'd
  (5 minutes), isolated per channel. Pure Node `EventEmitter` — no
  external dependency.
- **`src/lib/ai/latency-profile.ts`** — `recordMark` now forwards
  to the bus whenever the `req` id was linked to a `progressId`.
  Adds `shouldEmitMarks(reqId)` helper so pipeline gates can OR
  profiling with SSE subscriber presence. SSE emission is independent
  of `LATENCY_PROFILE=1` (prod stays quiet by default, opt-in per
  request via `progressId`).
- **`src/lib/ai/pipeline.ts`** — `__profileOn` snapshot now uses
  `shouldEmitMarks(__reqId)` so the pipeline's gated marks fire when
  a subscriber is linked, not just when `LATENCY_PROFILE=1`.
- **`src/app/api/generate/route.ts`** — accepts optional
  `progressId` in POST body (validated `[a-zA-Z0-9_-]{6,64}`),
  registers the channel, links the latency `reqId`, calls
  `completeProgress` on every terminal exit (success, clarify,
  refusal, 5xx) so subscribers close promptly.
- **`src/app/api/generate/progress/route.ts`** — new GET SSE
  endpoint. Requires auth. Validates id shape. Replays buffered
  events to late subscribers, heartbeats every 15s (keeps Vercel /
  nginx from killing the idle socket during a 30s asset-gen wait),
  hard-caps connection at 5 minutes. Closes on `done`, on client
  abort, or on TTL.

### Client

- **`src/hooks/useStudio.ts`** — `generate()` now opens an
  `EventSource` BEFORE the POST so even the earliest marks
  (`route.auth`, `route.body-parse`) are captured. Exposes
  `progressStage` (latest stage event). Closes the socket in
  `finally` so browser connection caps aren't exhausted.
- **`src/lib/generation-progress.ts`** — new `stageProgress(stage,
  elapsedMs)` maps server stage names to Korean copy + anchored
  percent (15/25/30/60/80/90/95). Unknown stages fall back to the
  TM-91 timer curve with a small "we got something" nudge.
- **`src/components/studio/PromptPanel.tsx`** — accepts
  `progressStage` prop. When present, derives copy/percent from
  the server stage; otherwise the existing TM-91 timer copy
  renders unchanged. Bar never moves backwards
  (`max(stagePct, timerPct)`).
- **`src/components/studio/Studio.tsx`** — wires `progressStage`
  from the hook into both desktop and mobile `<PromptPanel>`
  instances.

### Tests

## Design decisions

1. **Separate SSE endpoint, not streaming POST.** The POST
   handler still returns JSON because (a) it lets us preserve the
   existing client (`await res.json()`) without rewriting the
   parser, (b) clarify-mode responses, error envelopes, and the
   final asset payload all naturally fit JSON, (c) EventSource is a
   simpler client API than parsing a multipart SSE response from
   `fetch`.
2. **In-process pub/sub, not Redis.** EasyMake DEMO runs as a
   single Node instance (Vercel serverless: each generate request +
   its companion SSE stick to the same warm function instance for
   their short lifetime). Cross-instance fan-out would need Redis
   pub/sub; not justified at current scale and would conflict with
   ADR-0001 (edits are LLM-only, no Redis dependency required).
3. **Buffered + TTL'd channel.** The client opens EventSource
   then POSTs — but in failure modes (slow network, abort + retry)
   the POST might land first. Buffering for 64 events lets late
   subscribers catch up without losing context. TTL of 5 minutes
   handles abandoned streams.
4. **Timer fallback retained.** Browsers without `EventSource`
   (old IE-equivalent runtimes, server-rendered tests, headless
   bench drivers) see the unchanged TM-91 timer-based copy. The
   PromptPanel's `data-progress-source` attribute (`sse` vs
   `timer`) makes the fallback observable in DOM for QA.
5. **Bar never moves backwards.** Server stage events arrive out
   of order with the timer; we `max(stagePct, timerPct)` so a
   slow late stage event can't visually rewind the bar. Critical
   for perceived quality.

## Risks / known limits

- **EventSource same-origin only.** Acceptable — generate and
  progress endpoints share the origin.
- **Vercel function concurrency.** Each open EventSource holds a
  Node socket. The 5-minute hard cap + immediate close on `done`
  bounds usage at roughly N concurrent generates (typically 1
  per user session). Heartbeat is 15s.
- **`require('./progress-bus')` inside `recordMark`.** Dynamic
  require keeps `latency-profile.ts` importable from contexts
  that lack `node:events` (test envs). Cost is one `require.cache`
  hit per mark — negligible.
