# TM-118 — 회고

## 결과

- TM-108 r3 → r6 4회차 잔존했던 case 2 (long-video 60s) + case 3 (URL ingest HN) 의 `<Unknown>` EB **단일 root cause 식별 + fix + 라이브 검증** 1세션 내 완료.
- root cause: gpt-4o 의 `<lucide.Icon name="company-logo|hacker-news"/>` 환각 — lucide-react 의 `Icon` forwardRef 가 `iconNode.map(undefined)` 로 throw → React dev componentStack 이 displayName 없는 vendor forwardRef 를 `<Unknown>` 으로 표시.
- fix: `sanitizeForbiddenTokens` 의 §9 신규 rule — `<lucide.Icon name="...">` / `<Icon name="...">` 를 slug-mapping 사전 + Star fallback 으로 재작성. 정확한 자리에 정확한 한 줄.
- 검증: 라이브 재생성 후 case 2/3 둘 다 console 0 errors, 클린 렌더 (screenshot 첨부). 단위 테스트 5종 추가 (85/85 PASS).
- 비용: gpt-4o multi-step 4회 (pre-fix 2 + post-fix 2) ≈ $0.4.

## 잘 된 점

1. **prior 회차 회고를 first read** — r6 보고서가 "case 2/3 4회차 잔존, 동일 패턴" 까지 좁혀 둔 상태. 본 세션은 RCA 추출에만 집중 가능했다. TeamLead 패턴 (`wiki/05-reports/` first) 가 검증된 사례.
2. **라이브 콘솔 캡처 → 즉시 root cause** — Playwright MCP 로 dev 서버에 직접 connect, error stack 의 `node_modules_lucide-react_dist_esm_132c8s1._.js:198` 이 한 줄로 vendor source 를 지목. 추론 단계 없이 결정.
3. **SQLite 직조회로 생성 코드 검증** — `/api/assets/:id` endpoint 부재를 확인한 직후 prisma sqlite 직접 query 로 우회. 환각 슬러그 (`company-logo`, `hacker-news`) 가 두 case 모두 정확히 1회씩 등장 — RCA 신뢰도 100%.
4. **fix → 라이브 재생성 → fix 검증 cycle 이 단일 dev session 안에 완결** — turbopack HMR 덕분에 pipeline.ts 수정 즉시 다음 generate 가 새 코드 사용.
5. **TM-116/117 의 노력 보존** — TM-116 의 `__SceneBoundary` 는 본 fix 와 무관하게 여전히 *defense-in-depth* (vendor lib 가 다른 형태로 throw 할 때). TM-117 의 evaluator 명명 wrapper 도 stack 가독성에 기여. 이전 fix 를 폐기/회귀 없이 한 층 추가.

## 어려웠던 점 / 배운 점

1. **EB 트리거 vs. EB 처리 경로의 구분이 흐릿했었다** — TM-116/117 이 EB *처리* 안정화에 집중하다 보니 EB 를 *트리거* 하는 throw source 가 sanitize layer 에서 차단 가능하다는 옵션이 r5/r6 동안 간과되었다. 다음 회 EB 잔존 시 1단계로 "throw source 가 user-controllable 영역인가?" 를 먼저 확인.
2. **`<Unknown>` 시그니처가 evaluator wrapper 가 아닌 inner vendor forwardRef 였다** — TM-117 가설은 "evaluator wrapper 의 displayName 누락" 이었으나, 실제 stack 은 wrapper 한참 안쪽의 lucide.Icon. componentStack 을 stack-top 하나가 아니라 full chain 으로 읽었어야 했다. 본 회 에서는 Playwright `console_messages` 가 full stack 출력으로 직접 보여줘서 빠르게 교정.
3. **`lucide-react` 의 `Icon` named export 가 generic dynamic icon 이라는 사실** — 우리 prompts.ts 에는 "PascalCase named icons (Heart, Star, ...)" 만 가이드했고 `Icon` 이 vendor export 라는 사실은 명시 X. LLM 이 이걸 본 적이 있어서 환각으로 끌어왔을 가능성. prompt-level DO-NOT 추가가 보조 역할.
4. **NBSP / zero-width chars 가 Edit tool string match 를 깨뜨림** — 정확한 동일 byte 매칭 필요한 Edit tool 에서 sanitize layer 마지막에 NBSP 가 들어있는 라인이 매칭 실패. anchor 를 더 큰 컨텍스트로 옮겨 우회. 향후 sanitize 본문 안의 special-char block 근처를 수정할 땐 cross-context anchor 사용.

## next-time learning

- EB 잔존 회차가 발생하면 **콘솔 full stack** 을 1단계로 캡처 — vendor lib 가 throw 하는지 user code 가 throw 하는지에 따라 fix 위치가 완전히 달라진다 (prompt / sanitize / evaluator / runtime).
- lucide 처럼 displayName 없는 vendor forwardRef 가 `<Unknown>` 의 source 일 가능성을 첫 가설로 둘 것 — TM-118 의 4회차 잔존은 그걸 마지막 가설로 둔 비용이었다.
- prompt-level guardrail 은 sanitize-level guardrail 의 **선행** 이지 **대체** 가 아님. 항상 둘 다.
