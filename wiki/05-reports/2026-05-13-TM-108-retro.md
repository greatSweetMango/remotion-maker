# TM-108 — Asset full-text search (title + code + PARAMS)

## TL;DR

Dashboard 검색이 title뿐 아니라 generated code/PARAMS 본문까지 case-insensitive substring 매치.
MVP는 in-memory filter (옵션 A): 사용자별 asset 수가 작고 code/PARAMS가 KB 단위라 부담 미미.
Scaling 시 SQLite FTS5 virtual table로 후속 작업 권고 (옵션 B 별도 task spawn 권장).

## 무엇이 바뀌었나

- `GET /api/assets`에 `q` 쿼리 파라미터 추가. 존재 시 사용자 범위 row를 fetch → JS에서 `title + code + parameters` 대소문자 무시 substring 필터 → 페이징.
- 기존 `search` (title-only DB-side `contains`) 파라미터는 backward compat 유지.
- `AssetGrid.tsx`: 검색 input이 `q`를 전송하도록 변경 + placeholder "Search title, code, parameters…".
- 신규 단위 테스트 5건: title 매치, code/PARAMS 매치, partial substring (bear), 빈 q 전체 반환, q가 Prisma where에 push되지 않음 보장.

## 왜 / 배경

TM-87 (Asset v1) 완료 후 사용자가 코드/PARAMS 본문 키워드로 자산을 찾을 방법이 없었음.
Dashboard 검색의 가치를 높여 자산 재사용성을 강화.

## 영향

- 코드: `src/app/api/assets/route.ts`, `src/components/dashboard/AssetGrid.tsx`, `__tests__/api/assets/route.test.ts`.
- 사용자: 검색 인풋의 의미가 확장됨 (title only → title/code/PARAMS). UX는 동일 (input 1개).
- 성능: q 입력 시 페이징 전 전체 row를 메모리에 로드. 사용자당 자산 수가 수천 단위 미만이면 OK.

## 의사결정 (옵션 A vs B)

| 옵션 | 장점 | 단점 | 채택 |
|---|---|---|---|
| A. in-memory filter | 마이그레이션 불필요, 구현 단순 | row 폭증 시 메모리/시간 비용 ↑ | ✅ MVP |
| B. SQLite FTS5 virtual table + trigger sync | O(log n) 검색, scalable | Prisma raw SQL + custom migration + write 경로 trigger 관리 | 후속 task |

사용자 명시 승인 라인은 SQLite migration 포함이지만, 현재 데이터 사이즈에서 마이그레이션 비용/락이 가져다주는 이득이 작음 → A로 출시, B는 별도 task로 spawn.

## 후속 (spawn 권고)

- **TM-108-r2 (옵션 B)**: SQLite FTS5 virtual table — `asset_fts(title, code, parameters)` rowid ↔ Asset.id 매핑, INSERT/UPDATE trigger, Prisma migration custom SQL. q가 set일 때 raw `MATCH` 쿼리 → id 페이지 → Prisma에서 hydrate.
- 필요 조건: 사용자당 asset 수 > ~500 또는 `code` 평균 크기 > 50KB일 때 트리거.
