# TM-118 — case 2/3 `<Unknown>` EB 잔존 패턴 RCA + sanitize

## TL;DR

[[2026-04-27-TM-108-quality-benchmark-r6|TM-108 r6]] 가 r3 → r6 4회차 동일 잔존으로 격리한 case 2 (60s long-video) + case 3 (URL ingest HN 스타일) 의 `<Unknown>` ErrorBoundary 를, 라이브 dev 서버 + Playwright 콘솔 캡처로 **단일 root cause** 식별 후 fix.

**Root cause**: gpt-4o 가 두 prompt 패턴에서 결정적으로 환각하는 `<lucide.Icon name="company-logo"/>` / `<lucide.Icon name="hacker-news"/>` 호출. `lucide-react` 에는 그런 generic `Icon` API 가 **없다** — 실제 `Icon` export 는 `iconNode` array prop 을 요구하는 forwardRef 컴포넌트이며, `name` string 만 받으면 내부에서 `iconNode.map(...)` 호출이 `TypeError: Cannot read properties of undefined (reading 'map')` 로 폭발한다. React dev-mode 의 componentStack 은 displayName 없는 forwardRef 를 `<Unknown>` 으로 표시 — TM-116 의 displayName 작업이 잡지 못한 이유 (lucide 의 forwardRef 는 user code 가 아닌 vendor code 라 displayName 부여 통제 밖).

라이브 검증:
- **case 2 (60s long-video, asset cmp25xxpb)** — 콘솔: `<Unknown> 컴포넌트에서 발생`, `__SceneBoundary 가 처리`, 4× error log (mount + 2 frame). 코드 발췌: `lucide.Icon name="company-logo" color={scene0_primaryColor} size={100} />`.
- **case 3 (url-ingest HN, asset cmp25yd1w)** — 콘솔: 동일 시그니처, 코드 발췌: `lucide.Icon name="hacker-news" color={scene0_primaryColor} size={100} />`.
- 두 case 모두 동일 stack: `node_modules_lucide-react_dist_esm_132c8s1._.js:198 → updateForwardRef → <Unknown>`.

Fix 적용 후 (재생성):
- **case 2 (cmp26548f)**: `<lucide.Sparkles color={...} size={200}/>` 로 자동 치환, **0 console errors**, 클린 렌더.
- **case 3 (cmp265kck)**: `<lucide.Hash color={...} size={100}/>` 로 자동 치환, **0 console errors**, "Why we left the cloud" 헤드라인 정상 렌더 (HN orange `#ff6600`).
- 단위 테스트: pipeline.test.ts 80 → **85 통과** (+5 신규 TM-118 케이스), evaluator.test.ts 회귀 0.

### 3. lucide-react 내부 (왜 `<Unknown>` 인가)

lucide-react v0.x 의 `Icon` export 는 dynamic 아이콘 렌더용으로, props 시그니처:

```ts
const Icon = forwardRef(({ iconNode, ...rest }, ref) => {
  return createElement('svg', { ...rest, ref }, iconNode.map(([tag, attrs]) => createElement(tag, attrs)));
  //                                          ^ undefined.map → TypeError
});
// no displayName set → React shows it as <Unknown>
```

prompt 가 `<lucide.Icon name="..."/>` 를 emit 하면:
1. `iconNode` 가 undefined → `.map()` 에서 throw.
2. React dev-mode componentStack: forwardRef 의 함수 이름이 익명 (lucide 의 vendor build 가 .name 보존 안 함) + displayName 없음 → `<Unknown>` 표시.
3. TM-116 의 `__SceneBoundary` 가 잡아 transparent fill 로 graceful degrade — **그래서 다른 scene 은 렌더되고, case 2 의 인트로 scene1 만 빈 화면**.

### 4. 왜 case 2 + case 3 만 결정적으로 재현되었나

두 prompt 의 공통 패턴:

| 케이스 | trigger phrase | LLM 환각 슬러그 |
|---|---|---|
| 2 long-video | "인트로(로고+태그라인)" → 로고 필요 → "logo" 슬러그 | `company-logo` |
| 3 url-ingest | URL ingest 컨텍스트의 `source: https://news.ycombinator.com` → 사이트 로고 필요 | `hacker-news` |

baseline-simple (case 1) / chart (case 4) / typo (case 5) 는 로고/브랜드 컨텍스트가 없어 LLM 이 generic icon API 를 호출할 트리거가 없음 → 정확히 case 2/3 에서만 4회차 잔존.

### 5. 왜 TM-116 / TM-117 가 이걸 잡지 못했나

- **TM-116**: `__SceneBoundary` + scene component 의 displayName 부여 — 본 fix 는 boundary 가 정상 동작했다 (transparent fill). 하지만 boundary 가 잡은 **inner component** 인 lucide forwardRef 는 vendor code 라 displayName 통제 밖. componentStack 의 `<Unknown>` 은 lucide.Icon 자체.
- **TM-117**: evaluator wrapper 를 익명 arrow → 명명 function 으로 변경. wrapper 명명은 됐으나, throw 가 발생한 위치는 wrapper 가 아닌 **wrapper → Sequence → SceneBoundary → Scene1 → lucide.Icon (Unknown)**. wrapper 의 이름은 이미 EvaluatedAsset 으로 정상 표시되었고, 진짜 `<Unknown>` 은 stack 더 안쪽의 lucide forwardRef.

요약: TM-116/117 은 **EB 처리 경로** 를 안정화시켰지만, **EB 를 트리거하는 throw 자체** 는 잡지 못했다. TM-118 이 throw source (sanitize layer) 에서 차단.

## 무엇이 바뀌었나

### 1. `src/lib/ai/pipeline.ts::sanitizeForbiddenTokens` — rule §9 추가 (TM-118)

```ts
// 9. TM-118 — <lucide.Icon name="..."/> / <Icon name="..."/> hallucination.
const luxIconRe = /<\s*(?:lucide\.)?Icon\b([^/>]*)\bname\s*=\s*(?:["']([^"']*)["']|\{["']([^"']*)["']\})([^/>]*)\/?>/g;
if (luxIconRe.test(code)) {
  code = code.replace(luxIconRe, (_full, before, n1, n2, after) => {
    const slug = String(n1 || n2 || '').trim().toLowerCase();
    const map: Record<string, string> = {
      'hacker-news': 'Hash', 'hackernews': 'Hash', 'news': 'Newspaper',
      'logo': 'Sparkles', 'company-logo': 'Sparkles', 'brand': 'Sparkles',
      'cta': 'ArrowRight', 'arrow': 'ArrowRight', 'check': 'Check',
      'heart': 'Heart', 'star': 'Star', 'rocket': 'Rocket', 'flame': 'Flame',
      'trophy': 'Trophy', 'chart': 'ChartBar', 'graph': 'ChartBar',
    };
    const mapped = map[slug] || 'Star';
    const stripName = (s: string) =>
      s.replace(/\bname\s*=\s*(?:["'][^"']*["']|\{[^}]*\})/g, '').replace(/\s{2,}/g, ' ');
    return `<lucide.${mapped}${stripName(before)}${stripName(after)}/>`;
  });
  notes.push('rewrote <lucide.Icon name="..."/> hallucination to a real lucide icon');
}
```

전략:
- `<lucide.Icon name="...">` 또는 bare `<Icon name="...">` 매칭.
- slug → lucide PascalCase 매핑 (관찰된 슬러그 우선, 그 외 `Star` fallback).
- 다른 props (color, size, …) 보존, `name` 만 제거.
- sanitize layer 라 evaluator/transpiler 모두 통과 후 React 까지 도달했을 때 더 이상 throw 없음.

### 2. `src/lib/ai/prompts.ts` — DO-NOT 명시 추가

ICONS 섹션에 `**NEVER write <lucide.Icon name="..."/>**` 강조 문장 + "company logo → Sparkles, Hacker News → Hash/Newspaper" 가이드. 향후 회차에서 LLM 이 환각 빈도를 줄이도록 prompt-level fix.

### 3. 단위 테스트 5종 추가 (`__tests__/lib/ai/pipeline.test.ts`)

- `rewrites <lucide.Icon name="hacker-news"/> to <lucide.Hash/>`
- `rewrites <lucide.Icon name="company-logo"/> to <lucide.Sparkles/>` (props 보존 검증)
- `falls back to <lucide.Star/> for unknown slugs`
- `also handles bare <Icon name=...>` (no `lucide.` prefix)
- `does not touch correct <lucide.Star/> usage` (false-positive 차단)

## 영향

### 긍정

- **TM-108 r3 → r6 4회차 잔존 `<Unknown>` EB 패턴 100% 해소**. 라이브 0 console error, 클린 렌더.
- **multi-step pipeline 5/5 클린 렌더 목표 도달 가능성**: TM-108 r6 의 3/5 → r7 (재실행 시) **5/5** 기대. case 2/3 의 회복으로 평균 점수도 ~+10 예상 (50/70 → 65+/80+).
- **production 승격 경로 unblocked**: 이전까지 EB 노출은 user-visible UX 회귀였음. 이제 silent EB 사례 0건 — multi-step default-off 정책 재검토 가능.

### 잠재 리스크

- slug → 아이콘 매핑 사전 의 false-mapping (예: "graph" → `ChartBar` 가 user 의도와 다를 수 있음). 대안 fallback `Star` 도 prompt 부합도가 완벽하진 않으나, **EB 보다는 보임**. 시각적 fidelity vs. 안정성 tradeoff 에서 후자 선택.
- 본 sanitize 가 LLM 의 환각 자체를 줄이진 못함 — `prompts.ts` 의 DO-NOT 가이드가 보조 역할. 회차 모니터링 필요.
- 정규식이 multi-line attribute 를 못 잡을 수 있음 (`<lucide.Icon\n  name="..."\n />` 같은 LLM emit). 현재 케이스는 single-line 만 관찰되어 대응 OK, multi-line 변종 발견 시 §9 정규식 확장.
