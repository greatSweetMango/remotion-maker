# TM-184 — Multi-frame motion-liveness gate

사용자 보고 "애니메이션을 요청해도 생성물이 움직이지 않는다"에 대응하는 **positive liveness 게이트**. 기존 파이프라인의 모든 검증은 negative(deny-list/구조 reject)뿐이라 "렌더는 되지만 프레임 간 변하지 않는" 출력이 전 단계를 통과했다. 이 게이트가 그 공백을 메운다.

## 무엇을 했나

`src/lib/ai/liveness-check.ts` 신설 — 2-stage 게이트:

- **Stage 1 (AST, 무료)** `detectStaticMotionSource()` — 컴포넌트가 `useCurrentFrame/interpolate/spring` 등 frame-driven primitive를 0개 참조하면 렌더 없이 즉시 `static` 판정. TM-185의 `validateFrameDrivenMotion`(sandbox.ts CSS-freeze 축)을 **재사용**(중복 regex 구현 안 함). 일부 유닛 스위트가 `@/lib/remotion/sandbox`를 부분 mock 하는 경우를 위해 `typeof === 'function'` 방어 가드 추가.
- **Stage 2 (rendered diff)** 대표 프레임(0 / mid / last)을 renderStill로 뽑아 cross-frame feature diff < ε 이면 `rendered-frames-identical` static 판정. 1차 AST가 static을 잡으면 short-circuit(렌더 안 함).

## 핵심 결정 — 렌더 스테이지는 테스트 러너에서 기본 OFF

`isLivenessRenderEnabled()`:
- `AI_LIVENESS_GATE=0` → 전체 비활성
- `AI_LIVENESS_GATE_RENDER=0|1` → 명시 override가 항상 우선
- 그 외: **프로덕션(NODE_ENV≠test, JEST_WORKER_ID 없음)에서 ON, jest 러너에서 OFF**

이유: Stage 2는 Remotion 번들+renderStill을 띄우는 heavy 작업이라, generate 풀 경로를 도는 유닛 스위트(예: `generate-tm136-asset-gen.test.ts`)가 키 없이 **실제 렌더를 시도해 44s로 느려지고 flaky**해졌다(이번 작업 중 2회 에이전트 stall의 직접 원인). 테스트 러너에서 렌더 기본 OFF로 전환하니 generate 경로 테스트가 **44s → 0.56s**. 프로덕션 동작(character/scene 기본 ON)은 불변. 렌더 동작 자체를 검증하는 combined 테스트는 `__renderStill` mock + `AI_LIVENESS_GATE_RENDER=1` opt-in으로 커버.

## 검증

- `liveness-check.test.ts` 62/62 pass (정적 fixture FAIL, live fixture PASS, env-gating 3종, combined 5종).
- 광역 회귀 `__tests__/lib/ai` + `sandbox.test.ts`: 703 passed / 6 skipped, 1.3s.
- generate 경로: 54/54, 0.56s (실렌더 미발생 확인).
- tsc/eslint 변경 파일 clean.
