## Six-track summary

1. **Specialized agents** (5 new `.claude/agents/*.md`) — immediate.
2. **New MCPs** (`mcp__remotion-eval`, `mcp__llm-judge`, `mcp__prompt-corpus`) — build.
3. **New skills** (`prompt-tuning`, `remotion-validate`, `judge-acceptance`, `qa-iteration-bump`, `night-cycle`) — immediate.
4. **Orchestrator race fixes** — branch-locks flock mutex + spawned-ID reservation queue. **High priority** (active bug).
5. **Quality/cost dashboards** — `scripts/dashboard/roll-up.mjs` v1, `mcp__metrics` v2.
6. **Night-mode hardening** — codified STOP conditions, spend ledger, forward-progress check.

## Key findings

- The agent company already has the right primitives (`.claude/agents/`,
  Skill tool, MCP plugin pattern in `plugin/obsidian-mcp/`). Track 1
  and Track 3 are pure additive — no new infra needed, just new files.
- Track 4 (race conditions) is the only real **regression** in the
  current system. Both TM-55 and TM-85 lost work to it. Should not
  be deferred.
- Track 2 (new MCPs) is the highest-value but also highest-cost.
  Recommend gating each on parity tests against existing scripts.

## Costs

- This task: ~1 TeamLead iteration, no teammate spawns, no MCP calls
  outside research reads. Estimated token cost low (<$0.05).
- Follow-up tasks combined: estimated 30-50 TeamLead iterations,
  ~$5-10 spend.

## Risks / open questions

- Skill explosion: must enforce curation policy as part of T3. Suggest
  adding a `wiki/02-dev/skills-registry.md` index that requires PR
  review.
- MCP server uptime: `.mcp.json` is per-machine. When a new MCP is
  added, every contributor needs to restart their Claude Code session.
  Mitigation: each MCP must degrade gracefully (TeamLead falls back to
  existing scripts if MCP unreachable).
- Spawned-ID queue (T4) requires Orchestrator to be the **only**
  process draining it. If multiple Orchestrator sessions run (rare but
  possible during user-driven manual runs), we need a process-lock on
  Orchestrator itself. Out of scope here; flag in T7 implementation.
