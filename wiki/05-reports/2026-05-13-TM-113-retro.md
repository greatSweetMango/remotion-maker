# TM-113 retro — verdict-history.jsonl orchestrator append

## Problem

TM-101 의 STOP-guard 는 다섯 가지 신호 중 하나로 `error_rate_spike` 를 정의했다 — `.agent-state/verdict-history.jsonl` 의 최근 5건 verdict 중 `BLOCK`/`REQUEST_CHANGES` 비율이 60% 이상이면 STOP 자동 작성. 그러나 이 파일을 **쓰는 주체가 존재하지 않아** 신호가 항상 dormant 였다 (`!existsSync(path) → return null`). TeamLead 가 폭주(연쇄 BLOCK)해도 orchestrator 가 자동 멈추지 못함 → 야간 무인 운영 안전성 공백.

## Decision

Orchestrator Step 5 (TeamLead 요약 수집 직후) 에 verdict 1줄 append hook 을 추가. append-only JSONL + flock(mkdir mutex fallback) 으로 동시 머지 race 차단. 락 이름은 `.agent-state/verdict-history.lock`.

## Implementation

1. **`scripts/orchestrator/append-verdict.sh`** — 신규.
   - 인자: `<task_id> <verdict>`. `task_id` 는 `TM-N` 또는 bare `N` 모두 수용 → `TM-N` 으로 정규화.
   - verdict whitelist: `APPROVE | REQUEST_CHANGES | BLOCK` 외 거부 (exit 2).
   - 출력 라인: `{"ts":"<ISO-8601 ms>","task_id":"TM-N","verdict":"V"}`.
   - 동시성: `flock -w 10` (있을 때) 또는 `mkdir` mutex (macOS coreutils 없을 때). 10 병렬 호출에서 line loss / torn write 0.
   - 환경: `STATE_DIR` env 로 테스트 격리 가능.

2. **`.claude/commands/orchestrate.md` Step 5-verdict-log** — 신규 sub-section.
   - 요약 수집 직후 (5-pre 와 5의 verdict 분기 **사이**) 모든 summary 에 대해 1회 호출.
   - 머지 성공/실패와 무관 — best-effort telemetry. exit≠0 은 transcript 경고만.
   - `error_rate_spike` 신호가 비로소 활성화된다.

3. **`scripts/tests/test-append-verdict.sh`** — 9 케이스.
   - 5 verdict 패턴 sequential append (line count + JSON schema + 순서 + ID 정규화)
   - 잘못된 verdict / task_id / 인자 누락 → exit 2
   - 10 병렬 append → 10 라인 보존, 모두 well-formed (race safety)

## Verification

## Follow-up / risks

- Append hook 은 best-effort — 만약 append-verdict.sh 자체가 broken 이어도 orchestrator 본 흐름은 진행. 즉 STOP-guard signal 이 silently 꺼질 수 있음. 대응: 본 retro 의 verification 절차를 weekly status 에서 sanity-check (`.agent-state/verdict-history.jsonl` 라인 수가 머지 PR 수와 align 하는지).
- 파일은 무한히 커진다 (현재 rotation 없음). 분당 1 line 미만으로 1년 ≈ 0.5MB → 당분간 무시. 100MB 도달 시 rotation task spawn.
