# TM-179 retro — AudioContext error flood (TM-123 bypass via Player pre-allocated audio tags)

## User-blocking symptom

User reported 30+ `AudioContext encountered an error` lines in the studio
console even though TM-123's four-layer defense (sandbox deny, prompt
ban, evaluator deny, plugin deny) was confirmed shipped. Reproduced on a
fresh asset that contained NO `<Audio>` / `<CatalogueAudio>` reference.
TM-123 should have killed this cascade for visual-only assets, yet it
came back. Asset id from the bug report: `cmpaspov70001dmhlu5co33bc`.

## Root cause — Player-internal bypass

TM-123 only gates **generated code**. It does not touch
`@remotion/player`'s own runtime, which mounts up to
`numberOfSharedAudioTags` (default **5**) silent
`<audio src="data:..." preload="metadata">` elements via
`SharedAudioContextProvider`
(`node_modules/remotion/dist/cjs/audio/shared-audio-tags.js:343`). These
silent tags exist to sidestep Chrome's autoplay-policy on a *later* real
`<Audio>` mount (so the user's first interaction doesn't get a "play
denied" race), but they are mounted **unconditionally per Player mount**,
even when the composition contains no audio at all.

On a page that has not received a user gesture (fresh studio load,
SSR/CSR boundary, hot reload, asset switch via PARAMS), Chromium fails
the autoplay probe on each pre-allocated `<audio>` and emits
`AudioContext encountered an error` for each one — plus extras on the
suspend/resume cycle whenever the Player remounts. Five silent tags ×
multiple remounts during normal studio interaction = 30+ console lines.

The TM-123 verdict block correctly said "sandbox prevents `<Audio>` in
generated code." It was silent about the Player's own pre-allocation
path because that path is internal to `@remotion/player` and not visible
from a sandbox-static-analysis perspective. The 4-layer defence has zero
hooks into the Player wrapper; the cascade reappeared the moment users
loaded *any* visual-only asset whose audio-policy probe got blocked.

## Fix — gate `numberOfSharedAudioTags` per asset

Pass `numberOfSharedAudioTags={0}` to `<Player>` when the asset's
compiled JS contains no `<Audio>` / `<CatalogueAudio>` reference, and
keep the Remotion default (`5`) when it does. With zero, the silent-tag
pre-allocation is skipped entirely → no `<audio>` DOM nodes → no
autoplay-policy probe → Chrome stays quiet.

The detection is a small string-regex helper (mirrors the TM-123
sandbox boundary-regex shape so `<AudioBars>` / `<AudioVisualizer>`
custom components don't false-match). Operates on the stored `jsCode`
that the evaluator already consumes — no new transpile pass.

Also enabled `acknowledgeRemotionLicense` to remove one further
Player-emitted console line per remount (orthogonal noise reduction).

Note: Remotion's Player also hardcodes `audioEnabled: true` in
`SharedPlayerContexts` so the SharedAudioContext instance itself is
still created; we cannot avoid that without forking the Player. But the
`AudioContext` creation alone is silent — only the silent `<audio>`
tags trigger Chrome's autoplay-policy logger. Zero tags = zero noise.

## Why TM-123's verdict missed this

TM-123 was scoped to "generated code emits `<Audio>` with bad `src`."
The mental model was: "block the JSX tag, the cascade stops." That
model omitted the Player wrapper's own audio-tag pre-allocation, which
runs regardless of the composition contents. The signal that something
was off was visible in `node_modules/remotion/dist/cjs/audio/shared-audio-tags.js:343`
all along — but no test exercised the "visual-only composition,
Player-only audio noise" path because the only known reproducer was a
generated `<Audio>` (which TM-123 fixed).

Lesson: when wrapping a third-party Player that owns its own DOM
side-effects (audio tags, video tags, workers), sandboxing generated
content is necessary but not sufficient. Library-level props
(`numberOfSharedAudioTags`, `audioEnabled`, `acknowledgeRemotionLicense`)
that influence the wrapper's own DOM emissions must be set explicitly
for the EasyMake usage shape (mostly visual-only, occasional
CatalogueAudio) rather than left at library defaults aimed at general
video editors.
