# TM-109 — Asset custom thumbnail upload

## Scope

Per task spec: let users upload a custom thumbnail per `Asset`, persisted as
`Asset.thumbnailUrl`, surfaced on the dashboard `AssetCard`. Storage is
**local-only** (`public/uploads/thumbnails/<assetId>.<ext>`) — production
R2/S3 backing is a separate spawn task and intentionally out of scope here.

Constraints honored:
- No new npm dependencies (`git diff package.json package-lock.json` clean).
- Prisma migration via `prisma db push` (no migrations folder in this repo).
- Existing 95 asset-route tests continue to pass.

## What changed

**Schema** — `prisma/schema.prisma`
- New optional `Asset.thumbnailUrl String?`. Null = fall back to the existing
  Sparkles placeholder. Pushed via `npx prisma db push --skip-generate`
  (the worktree dev DB is the only sqlite file affected; main migration
  happens on PR merge via the same `db push` flow used for TM-107/108).

**API** — `src/app/api/asset/[id]/thumbnail/route.ts` (new)
- `POST` (multipart): validates session → `file` field → MIME ∈
  {png, jpeg, webp} (extension fallback for empty-MIME Safari uploads) →
  size ≤ 1 MiB → owner check → wipes any prior thumbnail for the asset
  across other extensions (avoids `<id>.png` *and* `<id>.webp` racing) →
  writes to `public/uploads/thumbnails/` → updates `Asset.thumbnailUrl`
  with a cache-busted URL (`?v=<sizeBytes>`) so the browser refetches when
  the same asset is replaced.
- `DELETE`: owner check → unlink any matching files (best-effort) → null
  out the column.
- Soft-deleted assets are treated as 404 — same convention as the other
  `/api/asset/[id]/*` routes (rename, tags, folder).

**Assets list** — `src/app/api/assets/route.ts`
- Added `thumbnailUrl: true` to the FTS-branch explicit `select`. The
  non-FTS branch already uses `include`, so it picks up the new column for
  free.

**Dashboard server query** — `src/app/dashboard/page.tsx`
- Pass `thumbnailUrl` through the serialized payload.

**UI** — `src/components/dashboard/AssetCard.tsx`
- Renders `<img>` when `thumbnailUrl` is set; otherwise the existing
  Sparkles placeholder. Plain `<img>`, not `next/image` — these are
  user-uploaded local files served from `/public`, so the Image optimizer
  buys nothing and would force `remotePatterns` config every new file.
- Hidden `<input type="file" accept="image/png,image/jpeg,image/webp">` with
  `MAX_THUMBNAIL_BYTES` mirrored client-side so we reject oversized files
  before burning a round-trip.
- Two new dropdown menu items: "Upload thumbnail" / "Replace thumbnail"
  (same handler, label switches on whether one already exists) and
  "Remove thumbnail" (only when one exists).

**Tests** — `__tests__/api/asset/thumbnail.test.ts` (new)
- 13 cases: 401, 400 (wrong content-type / missing file / empty), 415
  (unsupported MIME), 413 (oversize), 404 (missing or soft-deleted), 403
  (foreign owner), 200 happy path (file written under a tmp `process.cwd()`,
  DB updated with cache-busted URL), and DELETE cases (auth, missing,
  successful unlink + DB null-out).
- Pattern follows `tags-put.test.ts` (jest.mock auth + prisma).

## Decisions / trade-offs

- **Local FS, not R2/S3** — explicit per spec. Documented in the route file
  header that ephemeral filesystems on serverless deploys won't survive a
  redeploy. Spawn task: production storage migration.
- **`<img>` over `next/image`** — see code comment. User-uploaded paths are
  not statically known and the Image optimizer's resizing is overkill for a
  card thumbnail.
- **Cache-bust via `?v=<sizeBytes>`** — cheap and stable; size changes on
  re-upload so the browser sees a new URL without us touching
  `Cache-Control` on `/public`.
- **No `next/image` `remotePatterns` change** — keeps the Next config
  blast-radius zero.

## Out of scope (spawn candidates)

1. **R2/S3 storage migration** — pull the route's filesystem write behind
   the existing `getStorageProvider()` abstraction (already used by
   `/api/upload`). Adds a `kind: 'thumbnail'` provider key and wires the
   public URL through the storage response. Required before prod deploy
   on Vercel/serverless.
2. **Auto-generated thumbnails from rendered Remotion frame** — would
   reuse the same `Asset.thumbnailUrl` column; user upload becomes the
   override. Currently the Sparkles placeholder is a fine fallback.
