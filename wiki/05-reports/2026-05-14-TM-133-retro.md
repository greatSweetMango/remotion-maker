# TL;DR

User-blocking build error: landing page (`/`) failed to compile because
`src/lib/audio/manifest.ts` (TM-127) leaked `node:fs/promises` into the
client bundle via the TM-132 `<CatalogueAudio>` chain. Fixed by splitting
`manifest.ts` into `manifest-types.ts` (client-safe) + `manifest-loader.ts`
(`'server-only'`), exact same fix shape as TM-81 (prisma leak). Build now
green, all 58 audio tests pass, dev landing page returns HTTP 200 with no
chunking warnings.

# What was wrong

```
Code generation for chunk item errored
./src/lib/audio/manifest.ts — node:fs/promises
Import traces: manifest.ts → CatalogueAudio.tsx → evaluator.ts
  → TemplateCard.tsx → _LandingClient.tsx → page.tsx
```

Single file owned both the sync regex predicate (`isValidCatalogTrack`)
and the fs-touching `loadAudioManifest()`. `<CatalogueAudio>` only used
the predicate, but ESM evaluates the entire imported module — Turbopack's
client chunking context can't resolve `node:*`.

# What changed

| File | Action |
|---|---|
| `src/lib/audio/manifest-types.ts` | NEW — client-safe types, regex, `AUDIO_MOODS`, `isValidCatalogTrack`, `parseAudioManifest` |
| `src/lib/audio/manifest-loader.ts` | NEW — `'server-only'` sentinel + fs/crypto helpers (`loadAudioManifest`, `hashAudioAsset`, `verifyAudioCatalogueIntegrity`, `DEFAULT_MANIFEST_PATH`) |
| `src/lib/audio/manifest.ts` | NOW barrel — re-exports only the client-safe surface from `manifest-types` (loader intentionally NOT re-exported, would defeat the split) |
| `src/remotion/CatalogueAudio.tsx` | Imports `isValidCatalogTrack` from `manifest-types` (direct, documents intent) |
| `src/app/api/audio/manifest/route.ts` | Imports `loadAudioManifest` from `manifest-loader`, `AudioTrack` type from `manifest-types` |
| `__tests__/lib/audio-manifest.test.ts` | Imports split between `manifest-types` (parsers/types) and `manifest-loader` (fs helpers) |

No new npm dependencies (`server-only` already in lockfile via TM-81).

# Lessons

This is the **second** identical bundle-leak in two weeks (TM-81 was the
first, in `lib/usage.ts`). Pattern that bit us both times:

> A module that exports BOTH a sync pure function AND a top-level
> `import 'node:*'` will leak fs into the client bundle the moment any
> shared/component code imports the pure function.

Going forward, any new `src/lib/**` module with a `node:*` import MUST
either:

1. Live in a `<name>-loader.ts` (or similar) file that does **not**
   colocate client-safe exports, AND mark it `import 'server-only'`, OR
2. Be split day-one into `<name>-types.ts` + `<name>-loader.ts` if the
   client also needs types/predicates.

Suggested cheap audit: `rg -l "node:" src/lib/` cross-referenced with
`rg -l "from '@/lib/<that-module>'" src/{components,remotion,app/\(marketing\)}`.
