# TM-126 retro — Audio integration v2 policy ADR

## Goal

TM-123 shipped a hard "no audio" deny that fixed the `Html5Audio src
TypeError` cascade but left users who request BGM with no path forward.
This task is **research + ADR only — zero code change** — to decide
whether and how EasyMake re-introduces audio without re-opening the
TM-123 failure mode.

## Process

Three options compared (full text in ADR-PENDING-TM-126):

| Option | Sandbox-safe? | UX | Eng cost |
|---|---|---|---|
| (A) Permanent visual-only ADR | ✅ trivial | ❌ rejects "BGM" forever | 0 |
| (B) Curated `staticFile` catalogue + structural validator | ✅ via AST shape | ✅ preview-time audio | M (catalogue + 4 follow-up tasks) |
| (C) Post-render Lambda audio overlay (preview muted) | ✅ best | ⚠️ no preview sync | L (new UI + Lambda mix) |

Compatibility check against live ADRs (memorized in AGENTS.md):

- ADR-0001 (Edit ≠ Render): all three options compatible (no server
  render in edit path).
- ADR-0002 (PARAMS auto-extract): (B) leverages it (`bgmTrack` is just
  a PARAMS string); (A)/(C) don't touch it.
- ADR-0023 (PARAMS isolation): (B) compatible (track swap is single
  key); (C) bypasses entirely.
- ADR-0014 (sandbox hardening): (B) extends with structural rule, (A)
  is the existing baseline, (C) keeps it as-is.

## Decision

**Option B — Curated `staticFile` catalogue with literal-only `src`
validator.**

Rationale: only option that satisfies user BGM intent AND TM-123
sandbox invariant simultaneously. Validator narrows the allow-list to
literal `staticFile("audio/<name>.mp3")` calls so the TM-123 numeric/
dynamic `src` failure mode is structurally impossible.

(token: `ADR-PENDING-TM-126`). Orchestrator assigns NNNN at merge time.
