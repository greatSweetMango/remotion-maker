# TM-117 — Retro

## 잘 된 것

- **라이브 repro 우선 접근** — 막연한 가설 probing(`sucrase 가 어떤 토큰을 거부하는지`) 보다 실제 LLM 호출로 case 1 의 1:46 을 재현(`tm117-repro-case1.ts`, attempt 4/8). 페이로드를 디스크에 dump 한 덕에 root cause(literal `\n` double-escape) 가 즉시 보였다. ~$0.5 비용 대비 시간 절약 컸음.
- **r5 retro 의 가설 의심** — r5 는 "TM-114 sanitize 의 false-negative" 로 추정했으나 라이브 데이터는 다른 layer(LLM 출력 자체의 double-escape) 임을 드러냄. 가설 그대로 fix 했다면 또 다른 변종에서 재발할 위험.
- **defense-in-depth 결합** — root cause fix (`\n` un-escape) + 한 단계 위 방어 (per-scene transpile precheck) + 한 단계 더 위 (wrapper single-shot fallback). 세 layer 가 동시에 깨질 확률은 사실상 0.
- **단위 + 라이브 동시 검증** — 단위 75 통과 + 라이브 case 1 8/8 + 5-case 5/5. r6 재실행 전에도 PR 머지 의사결정 가능.

## 어려웠던 것

- **LLM 비결정성** — case 1 의 1:46 은 5 회 중 1-2 회만 재현. 첫 시도 5/5 OK 면 fix 했다고 오판할 위험. 8 회 실행으로 회피했지만 더 많은 회수가 필요할 수 있음.
- **`<Unknown>` 의 origin 추적** — EB componentStack 이 `<Unknown>` 으로 표시되는 정확한 origin (`Wrapped` arrow vs `GeneratedAsset` 익명 arrow vs SceneN inside SceneBoundary) 을 코드만 보고는 단정 어려움. 가설(`Wrapped` 가 dev-mode 에서 비결정적으로 익명 fallback) 로 명명 function 화 했지만 r6 라이브 데이터에서 최종 검증 필요.
- **directive/BOM 의 실제 발생 빈도 불명** — `"use client"`/zero-width 스트립은 라이브에서 한 번도 트리거되지 않음. 보수적 방어로 추가했지만 unnecessary 일 수 있음 (단, no harm).

## 다음에 적용할 것

- **fix task 의 라이브 repro 스크립트 의무화** — 본 task 의 `tm117-repro-case1.ts` 처럼 fix 가 잡으려는 패턴을 결정적으로(또는 5+ 회 stress 로) 재현하는 스크립트를 PR 에 첨부. 회귀 알람 + future debugging asset.
- **r6 직후 즉시 `<Unknown>` componentStack origin 최종 검증** — 만약 r6 에서 `<Unknown>` 이 다시 등장하면 본 fix 의 §3 (Wrapped 명명) 가설이 틀린 것 → DevTools 의 componentStack 출력을 직접 캡처해서 정확한 origin 식별 후 추가 fix.
- **LLM 출력 format 강제** — system prompt 에 "code MUST contain real newlines, NOT \\n escapes" 같은 directive 를 명시. 현재 prompt 는 JSON-string escape 규칙만 언급하고 실제 `\n` 의 의미는 불분명. 본 fix 의 §1 un-escape 가 잡고 있지만 prompt 단에서 차단하면 더 robust.
