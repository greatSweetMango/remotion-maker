# TM-97 retro — Spawned task canonical-ID reservation

## Problem

TeamLead sessions run inside a git worktree (`worktrees/TM-X-slug/`). The worktree's `.taskmaster/tasks/tasks.json` is a **stale snapshot** of `main` taken at worktree creation. When TeamLead (or a scheduler script like TM-94's refactor scheduler) called `task-master add-task` from inside the worktree, the freshly allocated ID was based on the stale tasks.json — collisions with canonical IDs on `main` were inevitable.

Observed instances:

- TM-94 recurring refactor scheduler spawned a task labelled "TM-82" (next free ID per its stale snapshot). The real TM-82 on `main` was the character-rendering task. Orchestrator had to manually reassign the new task as TM-110.
- TM-85 retro noted the same collision pattern with another worktree (since cleaned up).

PR merges further entangled this: code/wiki files merge cleanly, but `.taskmaster/tasks/tasks.json` conflicts almost every time, so the worktree's view of "I added TM-82" is silently discarded.

## Decision

**TeamLead never mutates `task-master` state from inside a worktree.** Spawned tasks travel as JSON proposals in the TeamLead summary, and the Orchestrator (canonical main repo) promotes them after PR merge.

## Implementation

1. **`scripts/orchestrator/check-cwd.sh`** — refuses any path under `worktrees/*` (string match) **and** any linked git worktree (detected via `git rev-parse --git-dir` ≠ `--git-common-dir`). Exit codes: `0` canonical, `20` worktree, `1` env error. Outputs machine-readable `WORKTREE=…\nPATH=…` lines.

2. **`scripts/orchestrator/promote-spawned.sh`** — Orchestrator-only. Reads a `spawned_tasks[]` JSON array (file or stdin):
   - calls `check-cwd.sh` on `$ROOT` first (self-guard, exit 20 if accidentally run inside a worktree),
   - acquires `flock` on `.agent-state/task-master.lock` (avoids races with other Orchestrator iters),
   - calls `task-master add-task` per entry,
   - extracts the canonical ID from stdout, falling back to scanning `.taskmaster/tasks/tasks.json` by title,
   - appends `triggers_requalify` metadata via `update-task --append` when provided,
   - returns a `[{placeholder_id, canonical_id, title}]` mapping so the Orchestrator can rewrite placeholder tokens in retro/wiki artifacts before commit.
   - Test escape hatches: `PROMOTE_DRY_RUN=1` (skip real add-task), `PROMOTE_SKIP_CWD_CHECK=1` (bypass worktree guard, test-harness only).

3. **`prompts/team-lead.md`** — rewrote the QA-spawn section. Old text instructed TeamLead to call `task-master add-task` directly; new text forbids it inside worktrees and documents the `spawned_tasks` JSON shape with a `placeholder_id` like `TM-46-spawn-1`. Linked the two new scripts.

4. **Tests** — `scripts/tests/test-check-cwd.sh` (5 cases: canonical pass, worktrees/* block, linked-worktree block, missing dir, machine-readable output) and `scripts/tests/test-promote-spawned.sh` (5 cases: empty array, malformed input, missing title, dry-run mapping, worktree guard). All pass.

## Open follow-ups

- Orchestrator command spec (`.claude/commands/orchestrate.md`) should be updated to call `promote-spawned.sh` in Step 5-pre. Not in this PR — separate orchestration-doc task recommended.
- `scripts/orchestrator/refactor-tick.mjs` currently calls `task-master add-task` directly (works because it runs in the main repo, not a worktree). It is unaffected by this change, but should adopt the same flock on `.agent-state/task-master.lock` in a future hardening pass.

## Considered alternatives

- (a) Have TeamLead `cd` to the canonical main repo and run `task-master add-task` there. Rejected: forces TeamLead to mutate `main` state mid-PR, defeating worktree isolation; also racy if multiple TeamLeads run in parallel.
- (c) Standalone ID-reservation service (`reserve-task-id.sh`). Rejected: more moving parts; the proposal/promote split already serializes through the Orchestrator and benefits from flock without a separate daemon.

The chosen design (TeamLead proposes, Orchestrator promotes) keeps responsibility for canonical state firmly on `main` and removes any path by which a worktree can corrupt the task DB.
