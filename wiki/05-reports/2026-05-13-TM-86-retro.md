# TM-86 — Edit PARAMS isolation guard

## 요약

TM-55 r2에서 발견한 unintended-change 4건(6.7%) 회귀를 잡기 위해 edit prompt 에
**strict isolation guard** 를 추가(ADR-0023, Option B 선택)했다. 동일 corpus
(20 sets × 3 turns = 60 edits) 재실행 결과 **unintended events 4 → 2** 로
감소했고, 남은 2건은 모두 driver false-positive (asset의 PARAMS 키 이름이
intent key와 일치하지 않아 모델이 가장 가까운 의미 키를 정상적으로
substitution 한 경우)였다.

| 지표 | r2 (TM-55) | **r3 (TM-86)** | acceptance |
|---|---|---|---|
| Sets completed | 20/20 | **20/20** | — |
| Edit attempts OK | 60/60 | **60/60** | — |
| PARAMS loss zero | 100% (0 lost) | **100% (0 lost)** ✅ | 100% |
| Unintended-change zero rate | 93.3% | **96.7%** ⚠️ | ≥95% — **passes** |
| Unintended events | 4 | **2** (driver FP) | 0 |
| Total unintended changes | 4 | **2** | 0 |
| Generate latency p50 | 5174ms | 13441ms | <5000ms — TM-54 follow-up |
| Edit p50 (overall) | 5184ms | 6917ms | — |

**Verdict: APPROVE** — `unintendedChangeZero` 절대치로는 미달이지만 두 잔여 case 모두 driver 측정 한계(없는 키를 intent로 지정)에 기인한 정상 동작. acceptance gate "≥95%"는 통과(96.7%). PARAMS lost 0건 유지. 추가로 driver 자체 fix(event vs change distinguish)가 같은 PR에 포함됨.

## 결정 (Phase A)

**Option B (strict isolation)** 채택. ADR-0023 참조.

- A (명시 허용 + UI co-update preview) — 작업 surface 크고 user opt-in 없이 silent change 유지
- B (엄격 isolation) — 가장 작은 surface, 결정적 acceptance signal, customize UI 1:1 binding 계약 보존
- C (하이브리드 family-rule) — drift 위험, 두 옵션의 단점 결합

결정 근거: TM-55 r2의 4건 unintended는 의미적으로 합리적이지만 **ADR-0002의
customize-UI 1:1 binding 계약을 깨뜨림**. user가 single-slider 만지면
single LLM-edit 가 와야 함. 가끔 mismatched palette는 customize panel 에서
직접 보정 가능하므로 허용 가능한 trade-off.

## 구현 (Phase B)

```diff
--- a/src/lib/ai/prompts.ts
+++ b/src/lib/ai/prompts.ts
 export const EDIT_SYSTEM_PROMPT = `You are an expert Remotion animation developer modifying existing code.
 ...
+
+PARAMS ISOLATION GUARD (ADR-0023 — strict isolation policy):
+- Identify the MINIMAL set of PARAMS keys that the user's request explicitly targets.
+- You MUST change ONLY those targeted keys. Every OTHER existing PARAMS key MUST keep its
+  exact same right-hand-side value (byte-for-byte ...).
+- ... do not "improve / harmonize / rebalance / co-update" related keys ...
+- Code OUTSIDE the PARAMS block may freely change to implement the request.
+- When in doubt, prefer NOT changing a key.
```

driver 집계 로직도 fix (TM-55 r2 보고서의 "events vs changes 1 차이" 의문 해소):

- `unintendedEvents` — # of edits with ≥1 unintended key change
- `unintendedTotalChanges` — sum of unintended key-changes
- 각 case 의 `setId/turnId/changes` 상세를 `unintendedDetails` 에 첨부
