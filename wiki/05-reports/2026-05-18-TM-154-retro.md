# TM-154 — CI wiring for circular-dependency guard

## Goal
Run TM-152's `npm run check:circular` (dependency-cruiser, `no-circular` rule, severity=error) on every PR that touches `src/**`, blocking merges that reintroduce import cycles.

## Change
Added `.github/workflows/check-circular.yml`:
- Triggers on `push`/`pull_request` to `main` when `src/**`, `.dependency-cruiser.cjs`, `package.json`, or the workflow file itself changes; plus `workflow_dispatch`.
- Steps: checkout (fetch-depth 1) → setup-node@20 → `npm run check:circular`.
- Mirrors the structure of TM-134's `lint-server-only-leaks.yml` for consistency.
- `permissions: contents: read` (least-privilege).

## Verification
- YAML parses cleanly (`js-yaml` load → top-level keys `name, on, permissions, jobs`).
- Local baseline: `npm run check:circular` → `0 violations (333 modules, 604 dependencies)` — exit 0.
- Workflow re-uses the exact npm script TM-152 introduced; no new dependencies or scripts.

## Caveat discovered (logged for follow-up, not blocking)
A synthetic cycle probe (`src/_tm154_cycle_probe/{a,b}.ts` importing each other) **did not** trigger a violation. Inspecting `--output-type json` shows `couldNotResolve: true` for the relative imports — dependency-cruiser is not resolving local TS files under `tsconfig.json`'s `moduleResolution: "bundler"`. Same outcome with `./b.js` extension or `@/...` path-alias forms.

Implication: the current `check:circular` guard reports 0 violations because the dependency graph is largely **unresolved**, not because cycles are absent. TM-152's audit relied on a different tool (madge) for the actual ↔ pair analysis, so the existing claim of "0 true cycles" is still credible — but the CI guard added here will only fire on cycles that dependency-cruiser actually resolves.

Recommended follow-up (spawned below): install `dependency-cruiser` as a devDep and configure `enhancedResolveOptions`/`webpackConfig` (or switch resolver) so TS/path-alias edges resolve. Then re-verify cycle detection end-to-end.
