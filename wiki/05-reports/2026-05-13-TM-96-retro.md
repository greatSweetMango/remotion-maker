# TM-96 Retro

## What

Closed the PR-duplicate race observed in TM-55 and TM-85, where
long-running background TeamLead sessions opened a second PR on a
branch that the main session had already merged.

Two cooperating guards landed:

1. `scripts/lib/branch-locks.sh` — bash mutex wrapper around every
   write to `.agent-state/branch-locks.json`. Prefers `flock(2)` on
   Linux/CI; falls back to an atomic `mkdir` mutex on macOS (no
   `flock` by default). All Orchestrator code paths
   (`set-entry`, `set-status`, `remove-entry`) now go through it.
2. `scripts/pre-pr.sh` — pre-PR hook called from TeamLead Phase D
   before `gh pr create`. Inspects `gh pr list --head <branch>
   --state all` and exits with state-specific codes (0/10/11/12) so
   the TeamLead prompt can branch: reuse existing PR, abort because
   already merged, or proceed.

## Why

TM-55 had two PRs for `feat/tm-55` (PR #126 merged, then a duplicate
opened by a background TeamLead). TM-85 had PR #132 merged followed
by PR #133 from commit `b39ddb0`, closed by user. TM-87 / TM-93 / TM-95
were near-misses caught by review only. Without a mutex, two
Orchestrator iterations can read/write `branch-locks.json` with stale
snapshots and lose entries; without a pre-PR check, `gh pr create` is
happy to open a second PR on a stale branch.

## How

### Mutex wrapper

- `flock --exclusive --timeout 30 --conflict-exit-code 75 9 -c ...`
  when `flock` is on PATH.
- macOS fallback: `mkdir .agent-state/branch-locks.mutex.d` is atomic
  on APFS. Bounded retry loop with stale-reap at `2 × timeout`
  (60s) by mtime. The reaper only fires when stat actually returns a
  numeric mtime — a vanished dir means another holder is finishing,
  not a stale lock (fix found during testing).
- Public CLI: `bash scripts/lib/branch-locks.sh
  {read,set-entry,remove-entry,set-status,with-mutex} ...`. Atomic
  write via `jq > tmp && mv` after JSON validation.

### pre-pr.sh

```text
exit 0  → safe (no PR for branch)
exit 10 → OPEN PR exists — push extra commits, comment, do NOT create
exit 11 → MERGED elsewhere — abort, report verdict=BLOCK to Orchestrator
exit 12 → CLOSED unmerged — allowed but must justify in body
exit 1/2 → env/usage error → escalate
```

Output is machine-readable: `STATE=…`, `PR_NUMBER=…`, `PR_URL=…`,
`PR_TITLE=…`. A `PRE_PR_GH_CMD` env var lets tests mock `gh`.

### Prompt + orchestrate.md updates

- `prompts/team-lead.md` Phase D — new step 7 calls `pre-pr.sh` and
  enumerates the rc → action matrix. PR creation moved to step 8.
- `.claude/commands/orchestrate.md` Step 3 / Step 5 / Step 5-block —
  every direct mutation of `branch-locks.json` replaced with a call
  to `scripts/lib/branch-locks.sh`.

## Verification

- `scripts/tests/test-branch-locks.sh`: 20 parallel `set-entry`
  writers + 20 parallel mixed `set-status`/`remove-entry`. Asserts:
  - final JSON valid (jq -e .)
  - all 20 entries present after the write phase
  - exactly 10 remaining + 10 blocked after the mixed phase
  - **5/5 stability runs PASS** (no dropped entries, no invalid JSON).
- `scripts/tests/test-pre-pr.sh`: six mocked `gh` payloads exercising
  exit codes 0/10/11/12, OPEN-beats-MERGED precedence, and
  machine-readable output. **All pass.**

First test run failed (19/20 entries) — root cause was the macOS
stale-reaper firing on a vanished mutex dir (stat fell through to
`echo 0`, making `age = now - 0 ≈ epoch`, which always exceeded the
threshold). Fixed by requiring `mtime > 0` before reaping. Fix
verified with five consecutive 20-writer trials.

## Lessons

- Atomic-mkdir mutex on macOS is fine **only if the stale-reaper
  treats "stat failed" as "another holder is racing me to clean up,"
  not as "lock is ancient." This is the bug that ate one of the 20
  entries on the first run.
- Pre-PR duplicate check belongs in TeamLead, not Orchestrator —
  Orchestrator never reaches that path for a backgrounded TeamLead.
- Machine-readable hook output (`KEY=VAL` lines) is more robust than
  JSON when the consumer is a markdown prompt parsing it by eye.

## Follow-ups

- (optional) `scripts/branch-locks-reconcile.sh` — periodic sweep
  that drops entries whose PRs are already merged.
- (optional) `pre-pr.sh` could also fail when zero commits ahead of
  origin/main, catching accidental empty PRs.
