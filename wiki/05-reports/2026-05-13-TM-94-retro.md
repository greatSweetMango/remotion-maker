# TM-94 Retro — Recurring refactor scheduler

## 목표

3일 주기로 "Code architecture & quality refactor" task 를 task-master 에 자동 등록하는 시스템. 사람이 잊지 않고 정기적으로 리팩터링 부채를 처리하도록 강제하는 메타 워크플로우.

## 구현 요약

세 가지 후보 중 **(c) 상태 파일 + Orchestrator tick** 채택.

- **이유**: cron 데몬/launchd 의존 0. 에이전트 컴퍼니가 idle 일 때도 다음 iter 시작 시 자연스럽게 평가됨. wake-up race 없음. ScheduleWakeup 체인보다 재시작 안전.
- (a) CronCreate, (b) ScheduleWakeup 체인은 follow-up 백업으로 보류.

### 산출물

| 경로 | 역할 |
|---|---|
| `.agent-state/refactor-cron.json` | scheduler state — `last_run_at`, `period_days=3`, `rotation_index`, `week_counter`, 6-area `focus_rotation`, `history[]` |
| `scripts/orchestrator/refactor-tick.mjs` | tick 스크립트. due 검사 → `task-master add-task` (manual 모드, AI 비용 0) → state 갱신. `--dry-run`, `--force`, `--state=`, `--tasks=`, `--json` flag 지원 |
| `.claude/commands/orchestrate.md` Step 1 | tick 호출 한 줄 추가. exit≠0 도 iter 진행 (best-effort) |

### Focus 순환 (6 areas, 18일 주기)

1. dead-code 제거 (ts-prune / depcheck)
2. circular dependency (madge / dependency-cruiser)
3. src/lib 모듈 응집도 (god-module 분해)
4. 테스트 커버리지 hot spot (vitest --coverage)
5. duplicate fragment (jscpd)
6. ADR vs 실제 코드 drift

`rotation_index` 가 매 spawn 마다 modulo 증가하므로 18일에 한 번 같은 주제가 돌아옴.

## 검증

| 시나리오 | 결과 |
|---|---|
| `--dry-run` | week=1 dead-code 예고만, state 변경 X |
| 실제 spawn (last_run_at 백데이트 상태) | **TM-82 "Refactor week 1: dead-code"** 등록 확인 (pending, medium) |
| 즉시 재실행 | `noop reason=not_due remaining_h=72` — idempotent |
| 격리 state(-4d backdate) + 격리 tasks.json 재실행 | week 2 circular-deps spawn 확인 (rotation 정상 advance) |

## 잔여 위험 / follow-up

- **history 무한 증가 방지**: 24 entry (≈2개월) 로 자동 트림. 그 이상 분석은 git log + transcript 로.
- **task-master add-task 출력 파싱 fragile**: id 회수 regex 실패 시 tasks.json 의 max id 로 fallback. 추후 task-master JSON output flag 가 안정화되면 교체.
- **manual 모드 사용**: AI 비용 0 트레이드오프로 task subtask 자동 생성은 없음. PM 이 픽업할 때 필요하면 `task-master expand --id=N` 추가 호출.
- **수동 비활성화 경로**: `.agent-state/refactor-cron.json` 의 `period_days` 변경 또는 파일 삭제. 후자 시 스크립트는 exit 1, orchestrator 는 iter 계속.

## 다음 iter 자동 효과

- 다음 orchestrator iter Step 1 에서 tick 호출 → not_due (72h 남음) → no-op.
- 5/15 ~16시 이후 부터 다시 due. 그때 spawn 되는 task = week 2 circular-deps (rotation index 1).
- PM 이 다음 ready fetch 시 TM-82 (medium priority, no deps) 를 자연스럽게 픽업.
