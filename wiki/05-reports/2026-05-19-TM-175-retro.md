# TM-175 — lucide hallucination scrub v2 (PascalCase invented icons)

## TL;DR

TM-118이 잡지 못한 두 번째 lucide 환각 클래스(`<lucide.Flowers/>`처럼 `name=` 없이 PascalCase로 위장한 가짜 export)를 lucide-react 실제 export 화이트리스트 기반 scrubber + validator로 차단. live `import * as Lucide`로 5,819개 valid name을 추출, 그 외는 fuzzy fix(`Flowers→Flower`, `CharacterIcon→User`, `SunRise→Sunrise` 등) 또는 `Star` fallback으로 자동 치환. plugin/remotion-eval에는 snapshot JSON으로 mirror (TM-115 sync 확장).

## 왜 / 배경

TM-118 (`2026-04-27-TM-118-fix.md`)은 `<lucide.Icon name="company-logo"/>` 같은 generic API 환각을 차단했지만, **`name=` 속성을 사용하지 않는 두 번째 클래스**가 남아 있었다. TM-166 RCA(`2026-05-18-TM-166-composition-rca.md`)의 corpus에서 실제로 관찰된 케이스:

```tsx
<lucide.Flowers .../>       // 실제 export는 `Flower` (단수)
<lucide.CharacterIcon .../> // 그런 이름 자체가 없음
<lucide.SunRise .../>       // 실제는 `Sunrise` (단일 단어 PascalCase)
```

이들은 TM-118 정규식(`Icon\b...name=`)을 우회하고 evaluator에 도달 → `lucide.Flowers === undefined` → React `Element type is invalid` throw → `<Unknown>` ErrorBoundary residue. TM-118 fix 이후의 잔존 패턴이다.

검증: 라이브 `Object.keys(require('lucide-react'))`로 확인.

| 입력 | 실제 lucide 존재? |
|---|---|
| `Flowers` | ❌ (`Flower` 만 존재) |
| `Stars` | ✅ |
| `Sparkle` | ✅ |
| `Cloudy` | ✅ |
| `SunRise` | ❌ (`Sunrise`) |
| `CharacterIcon` | ❌ |

→ heuristic 매핑은 안 되고, **lucide-react 자신의 export set이 single source of truth**.

## 영향

### 코드 / 시스템

- **defense in depth**: scrubber(`pipeline.ts §10`)가 1차 line, validator(`sandbox.ts`)가 2차 line. user-pasted code나 향후 신규 call site가 scrubber를 우회해도 sandbox가 catch.
- **lucide.Icon false-positive 회피**: `Icon`은 실제 export이므로 화이트리스트에 포함됨. TM-118 scrubber가 이미 `<lucide.Icon name=>` 변종을 먼저 잡으므로 충돌 없음. 테스트로 invariant 박제.
- **자동 fuzzy fix 신뢰성**: `LUCIDE_FUZZY_FIXES` 17개 entry. 단위 테스트(`every fuzzy-fix target is itself a real lucide export`)가 모든 매핑 target이 실제 lucide export임을 보장 — 오타 추가 시 즉시 fail.

### 사용자/제품

- TM-166 류 `<Unknown>` EB 잔존 0건 기대 (이미 TM-118로 case 2/3은 해소, 본 fix는 PascalCase 변종까지 보강).
- 사용자에게는 invisible — 화면에는 fallback icon(`Star` 또는 매핑된 의미적으로 가까운 icon)이 표시됨.

### 비용/성능

- 화이트리스트 set 1회 구축 (~5,819 entry, O(n) at module init, <5ms 측정). 이후 `Set.has` O(1).
- regex 스캔은 sanitize/validate path에 이미 존재하던 패턴 — 추가 비용 ≈ 0.
- snapshot JSON 126KB (plugin) — MCP 서버 startup에 1회 read.
