# TM-117 — multi-step 잔존 EB + 1:46 SyntaxError 해소

## TL;DR

[[2026-04-27-TM-108-quality-benchmark-r5|TM-108 r5]] 가 발견한 두 잔존 패턴 — case 1 의 `Unexpected token, expected "(" (1:46)` 회귀와 case 2/3 의 `<Unknown>` ErrorBoundary — 를 함께 fix.

세 축으로 hardening:

1. **`generateSceneCode` 의 literal `\n` un-escape (TM-117 §1)** — gpt-4o 가 `code` JSON 필드를 가끔 double-escape 해서 `JSON.parse` 결과가 LITERAL `\n` 2-char 시퀀스 + 개행 0개인 단일라인 페이로드로 반환되는 사례 직접 fix. 라이브 repro 로 attempt 4/8 에서 이 변종을 잡았다.
2. **`generateAssetMultiStep` 의 per-scene transpile precheck (TM-117 §2)** — composition 직전 각 scene 의 raw TSX 를 sucrase 로 개별 transpile 시도; 실패하는 fragment 는 displayName 보유 placeholder 로 교체. 다른 변종(예: 단일라인 + `//` 인라인 코멘트로 인한 (3:14) 실패) 까지 graceful degrade.
3. **`evaluator.ts` 의 `Wrapped` 익명 arrow → 명명 `function EvaluatedAsset` (TM-117 §3)** — r4/r5 의 `<Unknown>` EB componentStack 시그니처 제거. arrow function 에 `.displayName` 부여 후 React DevTools 가 dev-mode 에서 간헐적으로 `<Unknown>` 으로 표시하는 케이스 차단.
4. **`sanitizeForbiddenTokens` 의 directive/BOM/NBSP 스트립 (TM-117 §4)** — `"use client"`/`"use server"`/`"use strict"` directive + zero-width chars + non-breaking spaces 가 fragment head 에 박혀 sucrase 토큰화를 비결정적으로 깨는 케이스 방어.

라이브 검증:
- **case 1 stress (8 회 동일 프롬프트)**: r5 직전 4/5 fail (1:46) → TM-117 **8/8 PASS**. attempt 4/6 에서 literal `\n` un-escape 트리거 확인.
- **5 case full pipeline (`tm-116-pipeline-direct.ts`)**: r5 직전 4/5 (case 1 회귀 + case 2/3 EB) → TM-117 **5/5 generate + 5/5 evaluator PASS**.
- 단위 테스트: pipeline 54 → **62 통과** (+8 신규), evaluator 14 → **15 통과** (+1 신규). 회귀 0. 전체 jest suite: pre-existing 8 fail (visual-regression / a11y, TM-117 와 무관) 유지.

이로써 TM-108 r6 재실행 시 multi-step **5/5 클린 렌더** 목표가 달성 가능. multi-step default-off 정책은 유지 (비용 ratio + 품질 격차는 별도 task), enable 시 EB 노출 0% 가 본 fix 의 가치.

## 무엇이 바뀌었나

### 1. `src/lib/ai/pipeline.ts::generateSceneCode` — literal `\n` un-escape

gpt-4o 가 가끔 `"code"` 필드를 double-escape 해서 emit (모델 출력 자체에 `\\n` 으로 escape) → `JSON.parse` 후 결과 문자열에 LITERAL `\n` 2-char 시퀀스가 들어 있고 실제 개행은 0개. 라이브 repro (`__tests__/benchmarks/tm117-repro-case1.ts`) attempt 4 에서 캡처된 실제 fragment:

```
const Scene1Params = {\n  scene0_primaryColor: '#1E3A8A', // type: color\n  scene0_speed: 1, // type: range\n};\n\nexport const Scene0 = ({...}) => {...}
```

sucrase 는 `\` 를 identifier-escape prefix 로 시도하다 인접 토큰에서 실패하고 `(1:46)` 으로 보고. fix:

```ts
if (!/\n/.test(rawCode) && /\\n/.test(rawCode)) {
  rawCode = rawCode
    .replace(/\\r\\n/g, '\n').replace(/\\n/g, '\n')
    .replace(/\\t/g, '  ').replace(/\\"/g, '"').replace(/\\'/g, "'");
}
```

heuristic: real newline 이 하나도 없고 literal `\n` 만 있는 경우에만 동작 — well-formed 멀티라인 코드의 string literal 안 `\n` 은 보존.

### 2. `src/lib/ai/pipeline.ts::generateAssetMultiStep` — per-scene transpile precheck

composition 직전 각 scene fragment 를 개별적으로 `transpileTSX` 시도. 실패 시 (`Unexpected token` 등) 해당 fragment 를 displayName 보유 placeholder 로 교체:

```ts
const prechecked = await Promise.all(
  sceneCodes.map(async (frag, i) => {
    try { await transpileTSX(frag); return frag; }
    catch (err) {
      const n = i + 1;
      return `const Scene${n}Params = {};\nconst Scene${n} = () => <AbsoluteFill style={{ backgroundColor: 'transparent' }} />;\nScene${n}.displayName = ${JSON.stringify(`Scene${n}`)};`;
    }
  })
);
const composedCode = composeSceneCodes(outline, prechecked);
```

defense-in-depth: §1 un-escape 가 모든 변종을 잡지 못해도 (예: 단일라인 + `//` 인라인 코멘트로 인한 `(3:14)` 실패) composition 자체는 절대 깨지지 않음. EB 결과는 `<Scene{N}>` placeholder 하나만 transparent 로 표시, 다른 scene 은 정상 렌더.

### 3. `src/lib/remotion/evaluator.ts` — `Wrapped` 익명 arrow → 명명 function

```ts
// Before
const Wrapped: RemotionComponent = (props) => React.createElement(inner, props);
Wrapped.displayName = 'EvaluatedAsset';

// After
function EvaluatedAsset(props: Record<string, unknown>) {
  return React.createElement(inner, props);
}
const Wrapped = EvaluatedAsset as RemotionComponent;
Wrapped.displayName = 'EvaluatedAsset';
```

React 의 dev-mode componentStack 은 arrow function 에 후행 부여된 `.displayName` 을 간헐적으로 무시하고 `<Unknown>` 으로 표시. 명명 function declaration 은 `function.name` 이 construction time 에 설정되므로 React 가 항상 픽업 가능. TM-108 r4/r5 의 case 2/3 `<Unknown>` 시그니처 직접 원인.

### 4. `sanitizeForbiddenTokens` — directive/BOM/NBSP 스트립

```ts
// "use client"/"use server"/"use strict" head directives
const directiveLine = /^[ \t]*['"]use (?:client|server|strict)['"];?[ \t]*\r?\n?/gm;

// zero-width / BOM characters (U+FEFF, U+200B-U+200D, U+2060)
if (/[﻿​-‍⁠]/.test(code)) { code = code.replace(/[﻿​-‍⁠]/g, ''); }

// non-breaking spaces (U+00A0) → regular space
if (/ /.test(code)) { code = code.replace(/ /g, ' '); }
```

gpt-4o 가 prompt 컨텍스트(특히 doc-style URL ingest)에서 zero-width / NBSP 를 carry-over 하는 경우 + Next.js 친화적으로 `"use client"` 를 자동 추가하는 경우 방어. 본 fix 가 case 1 1:46 의 root cause 였을 가능성은 낮지만 (`\n` un-escape 가 직접 원인이었음) 인접 failure mode 정리.

## 왜 / 배경

r5 분석은 두 패턴을 식별했다:

1. **case 1 의 1:46 SyntaxError** — r3 에서 처음 등장, TM-114 가 잡았다고 판단했으나 r5 에서 재발. r5 retro 가설은 "TM-114 sanitize 의 false-negative". 실제 root cause 는 다른 layer: **gpt-4o 의 `code` 필드 double-escape** 로 인한 single-line 페이로드. TM-114 의 require-strip 와 무관.
2. **case 2/3 의 `<Unknown>` EB** — r3 부터 잔존, TM-116 이 GeneratedAsset/SceneN/SceneBoundary 에 displayName 부여 후에도 case 2/3 에서만 잔존. 원인은 evaluator wrapper 의 익명 arrow + 후행 displayName 패턴 — React dev-mode 의 비결정적 픽업 실패.

본 fix 는 두 root cause 를 직접 fix + defense-in-depth (per-scene precheck + directive 스트립) 추가.

### 잠재 리스크

- per-scene transpile precheck 가 `transpileTSX` 를 scene 수만큼 추가 호출 (대부분 < 10ms 짧은 fragment) — overhead ≤ 50ms × 12 scenes = 0.6s 최악. multi-step pipeline 총 20-30s 대비 무시 가능.
- `un-escape` heuristic 의 false-positive 가능성 — well-formed 멀티라인 코드 안에 literal `\n` 만 있는 case 는 실재할 수 있으나, 현재 condition (`!/\n/.test() && /\\n/.test()`) 로 회피. real newline 이 하나라도 있으면 trigger X.
