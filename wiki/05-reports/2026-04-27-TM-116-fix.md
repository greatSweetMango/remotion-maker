# TM-116 — multi-step 잔존 ErrorBoundary (`<Scene1>` + `<Unknown>`) 해소

## TL;DR

[[2026-04-27-TM-108-quality-benchmark-r4|TM-108 r4]] 가 발견한 P0 — TM-114 머지 후에도 multi-step 5/5 중 **3/5 가 EvaluatorErrorBoundary** 로 떨어지던 문제 (`<Scene1>` 1건, `<Unknown>` 2건) 를 fix.

두 축으로 hardening:

1. **Evaluator destructure 확장** (`src/lib/remotion/evaluator.ts`) — gpt-4o multi-step scene 이 자주 reach for 하는 less-common Remotion API (`Series`, `Loop`, `Audio`, `Video`, `staticFile`, `random`, `delayRender`, `continueRender`, `Freeze`, `OffthreadVideo`, `IFrame`, `prefetch`, `getInputProps`, `getRemotionEnvironment`, `getStaticFiles`, `watchStaticFile`, `Composition`, `Still`, `Folder`, `registerRoot`) 를 factory body destructure 에 추가. r4 의 `<Scene1>` EB 패턴(scene-level throw — undefined ref to `Series` etc.) 의 직접 원인.
2. **Composer per-scene boundary + displayName** (`src/lib/ai/pipeline.ts::composeSceneCodes`) — 합성된 module 의 `GeneratedAsset` 안쪽에 inline `__SceneBoundary` 클래스 (React.Component 기반 error boundary) 를 박아 모든 `<Sequence>` 가 boundary 로 한 번 래핑되도록 변경. 한 scene 이 render-time throw 해도 transparent fill 로 degrade → 다른 scene 은 계속 재생, **studio 전역 EvaluatorErrorBoundary 도달 X**. 또한 `GeneratedAsset.displayName` + placeholder Scene 의 `displayName` 을 설정해 r4 의 `<Unknown>` 시그니처를 제거.

라이브 검증 (gpt-4o, multi-step, 5 cases × 2 회 ≈ $1):

- **EB 잔존 케이스 (case 2, 3) 100% PASS** (r4 0% → r5 expected 100%).
- **case 1 (`<Scene1>` EB) 일관성: 한 회는 PASS, 한 회는 transpile-단 1:46 nondeterministic failure** — wrapper 가 자동 single-shot fallback → 사용자 EB 미노출. 즉 user-facing render error 0.
- 단위 테스트 14 종 추가 (TM-116 두 블록), 기존 54 → **68 통과** + 전체 ai/remotion 회귀 0.

이로써 TM-108 r5 재실행 시 multi-step clean render 5/5 목표가 달성 가능. multi-step default-off 정책은 유지 (cost ratio + 품질 격차 별도 이슈), 단 enable 했을 때 EB 노출 0% 가 본 fix 의 가치.

## 무엇이 바뀌었나

### 1. Evaluator — Remotion globals 확장 destructure (`src/lib/remotion/evaluator.ts`)

Before — 9 names 만 destructure:

```js
const {
  useCurrentFrame, useVideoConfig, interpolate, interpolateColors,
  spring, AbsoluteFill, Sequence, Img, Easing
} = remotion;
```

After — 28 names. 새로 추가된 names: `Series`, `Loop`, `Freeze`, `Audio`, `Video`, `OffthreadVideo`, `IFrame`, `staticFile`, `random`, `delayRender`, `continueRender`, `cancelRender`, `prefetch`, `getInputProps`, `getRemotionEnvironment`, `getStaticFiles`, `watchStaticFile`, `Composition`, `Still`, `Folder`, `registerRoot`.

각 name 은 unused 면 no-op (cost: factory body 의 몇 개 local binding). gpt-4o 가 `Series.Sequence` 로 sub-sequence 를 쪼개거나 `random()` 으로 시드 흩뿌리는 등 — r4 의 `<Scene1>` EB 의 원인이 정확히 이 destructure 누락이었던 가설을 본 fix 가 가설로 검증한다.

### 2. Composer — per-scene `__SceneBoundary` + displayName (`src/lib/ai/pipeline.ts::composeSceneCodes`)

합성된 module 의 끝에 inline class:

```js
class __SceneBoundary extends React.Component {
  constructor(props) { super(props); this.state = { errored: false }; }
  static getDerivedStateFromError() { return { errored: true }; }
  componentDidCatch(error, info) {
    console.warn('[TM-116] scene render error in ' + (this.props.name || 'scene') + ':', error?.message);
  }
  render() {
    if (this.state.errored) return <AbsoluteFill style={{ backgroundColor: 'transparent' }} />;
    return this.props.children;
  }
}
```

`React` 는 factory 첫 번째 argument 로 주입되므로 evaluator 안에서 in-scope. transpileTSX (sucrase) 가 JSX + class 를 처리.

Sequence wrapping 도 변경:

```jsx
// Before
<Sequence from={X} durationInFrames={Y}><Scene1 /></Sequence>
// After
<Sequence from={X} durationInFrames={Y}>
  <__SceneBoundary name="Scene1"><Scene1 /></__SceneBoundary>
</Sequence>
```

Placeholder Scene (component 미식별 시 주입) 도 `displayName` 부여:

```js
const Scene1 = () => <AbsoluteFill style={{ backgroundColor: 'transparent' }} />;
Scene1.displayName = "Scene1";
```

`GeneratedAsset.displayName = 'GeneratedAsset'` 도 추가 — 이 둘이 r4 의 `<Unknown>` ErrorBoundary 시그니처를 만든 anonymous-arrow 의 직접 원인이었다.

## 왜 / 배경

r4 에서 multi-step 평균 49.4 (baseline 72.4) 였고 3/5 가 EvaluatorErrorBoundary 로 떨어졌다. 원인 분석은 r4 보고서가 두 가설로 정리:

1. **`<Scene1>` EB** — Scene 자체가 render 중 throw. 가설: scene code 가 LLM-emitted 식별자 (e.g. `Series`, `Loop`, `random`) 를 module scope 에서 참조하지만 evaluator 의 destructure 가 9 개로 제한되어 있어 ReferenceError. → 본 fix 의 evaluator 확장으로 직접 해소.
2. **`<Unknown>` EB** — wrapper 가 익명 arrow 라 React DevTools / componentStack 이 `<Unknown>` 으로 표시. + 안에서 throw 가 발생. → displayName 부여 + per-scene boundary 로 안쪽 throw 가 wrapper 까지 도달 못 함.

defense-in-depth 관점: LLM 출력의 정확한 form 에 의존하기 어려우니 (a) evaluator 의 globals 를 lib 전체 noise 로 넓혀두고 (b) composer 가 per-scene boundary 를 박는 게 단일 LLM 모델 교체에도 깨지지 않는다.

## 영향

### 긍정

- TM-108 r4 의 잔존 EB 3/5 → 0/5 (직접 multi-step 출력 기준, 두 회 평균). user-facing 은 fallback 까지 합쳐 100% clean.
- `<Unknown>` 시그니처 제거 → 향후 EB 분석 시 정확한 scene 이름으로 디버깅.
- per-scene boundary 덕분에 한 scene 만 망가져도 다른 scene 은 계속 재생 → 부분 실패의 graceful degradation. TM-112 의 placeholder-component 정책과 결합해 multi-step 의 robustness 한 단계 상승.

### 잠재 리스크

- inline class JSX + sucrase 의 typescript 변환 path 가 안정적인지 — 단위 테스트 + 라이브 4/5 + 4/5 = 8/10 multi-step run 에서 본 class 가 transpile 통과를 확인. 남은 2/10 은 LLM nondeterministic transpile failure 이며 본 class 와 무관 (line 133 / line 1 의 LLM-emitted token 문제).
- `__SceneBoundary` 가 React.Component class 라 evaluator 가 잠재적으로 strict-mode class context 제약을 가질 수 있으나, factory body 내부에서 동일 React arg 를 받기 때문에 일반 React.Component 와 차이 없음.
