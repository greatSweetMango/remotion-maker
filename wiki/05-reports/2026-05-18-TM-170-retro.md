# TM-170 retro — opaque-fill-above-Img composition lint

PR: https://github.com/greatSweetMango/remotion-maker/pull/213
Branch: `feat/tm-170-composition-lint`
Depends on: TM-166 (RCA), TM-99 (sandbox)
Closes RCA Axis 3 from [[2026-05-18-TM-166-composition-rca|TM-166 RCA]].

## What shipped

- `src/lib/remotion/sandbox.ts` — new `detectOpaqueOverlayAboveImg(code)` invoked from `validateCode`; rejects an empty, no-`opacity:` overlay (`<AbsoluteFill backgroundColor:>` or `<div position:'absolute' width:'100%' backgroundColor:>`) emitted AFTER a subject `<Img>` in source order.
- `plugin/remotion-eval/src/validate.ts` — TM-115 mirror.
- `src/lib/ai/prompts.ts` — `SCENE_CODE_SYSTEM_PROMPT` RULE #6 documents the rejection so the multi-step LLM path stops emitting the pattern.
- `__tests__/lib/remotion/sandbox.test.ts` — 7 new cases (verbatim TM-166 shape, AbsoluteFill variant, + 5 legal-pattern negatives).
- `plugin/remotion-eval/test/validate.test.ts` — 4 mirror cases.

Result: in-app sandbox 62/62 green, plugin 36/36 green.

## Design choices

- **Regex, not AST.** Sandbox already runs regex deny-list per edit; adding a parser would inflate edit latency. The lint's conservativeness (4 conjunctive conditions: after-Img, empty, no-opacity, width:'100%' for div) keeps false-positive surface narrow.
- **Hard error, not warning.** TM-166 was user-blocking; warnings without enforcement get ignored by the LLM. The error message includes "TM-170 — fade with opacity or remove" so the edit-path retry has a concrete fix.
- **System prompt addendum + validator.** Prevention + enforcement. The prompt rule lets the LLM avoid the pattern on first emission; the validator catches it when the LLM still slips.
